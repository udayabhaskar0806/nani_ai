# N.A.N.I. V2 — PERSONAL AI COMPUTER OPERATING AGENT

## 1. PROJECT MISSION

N.A.N.I. stands for:

Neural Analytical Network Intelligence.

N.A.N.I. is NOT intended to be another chatbot.

N.A.N.I. must become a persistent general-purpose autonomous computer agent running on top of Ubuntu Linux.

The user communicates with N.A.N.I. initially through text chat.

The user should provide HIGH-LEVEL OBJECTIVES rather than step-by-step commands.

Example:

User:
"Open my embedded project, understand the code, find the problem, fix it, build it, test it and show me the result."

N.A.N.I. must determine the intermediate steps itself.

Future versions will add voice, but voice MUST NOT be part of the initial implementation.

The architecture must therefore keep input/output interfaces independent from the intelligence and agent runtime.

---

# 2. PRIMARY DESIGN PRINCIPLE

The system must operate using:

GOAL
→ UNDERSTAND
→ OBSERVE
→ PLAN
→ ACT
→ OBSERVE RESULT
→ VERIFY
→ REPLAN IF NECESSARY
→ CONTINUE
→ FINAL VERIFICATION
→ REPORT

N.A.N.I. must NOT assume that an action succeeded merely because it executed a command or clicked something.

Every meaningful action must produce observable evidence.

---

# 3. TARGET EXPERIENCE

Example 1:

User:

"NANI, fix my SPI driver."

N.A.N.I. should autonomously:

1. Determine which project the user means using context/memory.
2. Locate repository.
3. Inspect repository.
4. Check Git state.
5. Understand project structure.
6. Locate relevant SPI code.
7. Understand build system.
8. Reproduce problem.
9. Analyze compiler/runtime errors.
10. Research documentation if necessary.
11. Modify appropriate files.
12. Build.
13. Detect failures.
14. Diagnose.
15. Modify again.
16. Rebuild.
17. Run tests/static checks.
18. Inspect Git diff.
19. Verify requested behavior.
20. Open/show project in VS Code when useful.
21. Report exactly what changed and why.

The user should NOT have to tell N.A.N.I.:

"run make"
"open this file"
"change line 150"
"compile again"

N.A.N.I. decides those intermediate actions.

# 5. DO NOT USE GUI WHEN A BETTER INTERFACE EXISTS

N.A.N.I. should behave intelligently rather than copying human inefficiency.

Preferred execution order:

1. Native API / MCP / structured integration
2. Filesystem/system API
3. CLI
4. Browser DOM / Playwright
5. Desktop accessibility interface
6. Screenshot + vision + mouse/keyboard

Example:

To read a 5000-line source file:

WRONG:
scroll through VS Code and visually read everything.

RIGHT:
read the source file directly.

To compile:

RIGHT:
execute compiler directly and capture stdout/stderr.

VS Code can still be opened so the user can observe the result.

GUI automation is the universal fallback, not the primary interface.

# 7. AGENT LOOP

Conceptually implement:

while task is not finished:

    observe current environment

    retrieve relevant memory

    reason about current state

    decide next action

    select appropriate tool/agent

    execute action

    capture result

    compare expected vs actual result

    store action and observation

    if action failed:
        diagnose
        modify plan
        retry using another strategy

    if objective appears complete:
        independently verify completion

        if verification succeeds:
            finish task

        otherwise:
            continue execution

The exact implementation can use an existing reliable agent framework rather than recreating this entire runtime manually.

# 10. CODING AGENT

Do NOT create a complete autonomous coding agent from scratch.

Evaluate and integrate mature open-source coding-agent projects.

The coding worker must support:

- repository exploration
- semantic/code search
- file reading
- file editing
- patch generation
- shell commands
- builds
- tests
- Git status
- Git diff
- debugging
- iterative error correction

OpenHands should be evaluated first.

Example:

→ CodingAgent
→ OpenHands adapter
→ repository

SEMANTIC MEMORY:

# 18. RECOVERY ENGINE

Failure must NOT immediately return control to user.

Recovery sequence:

ACTION FAILED
↓
inspect error
↓
identify probable cause
↓
retry if transient
↓
try alternative method
↓
research if necessary
↓
replan
↓
continue

Examples:

GUI button failed:
→ retry once
→ keyboard shortcut
→ accessibility interface
→ CLI/API alternative

Build failed:
→ inspect compiler error
→ inspect relevant source
→ fix
→ rebuild

Browser selector failed:
→ refresh state
→ inspect DOM again
→ alternate selector
→ vision fallback

Set loop limits.

Detect repeated identical failures.

Never retry indefinitely.

---

# 19. VERIFICATION ENGINE

N.A.N.I. must prove task completion.

Coding verification:

- build passes
- tests pass
- expected files exist
- Git diff inspected
- unexpected modifications detected

Browser verification:

- correct page/state reached
- selected values checked
- dates/prices/options verified

Desktop verification:

- expected application/window state exists

System verification:

- compare system state before and after

The executor should not be the sole authority deciding whether its own work succeeded.

# 21. SECURITY MODEL

High autonomy does NOT mean unlimited privilege.

Use task-scoped autonomy.

LOW RISK:
automatic

Examples:
read project
compile
test
inspect system
web research

MEDIUM:
automatic but logged

Examples:
modify project files
start/stop development applications

HIGH:
require confirmation

Examples:
financial transaction
purchase
send external message
publish code
delete important data
major system-security change
credential operation

Never expose secrets directly to models when avoidable.

Use sandboxing for experimental code execution.
